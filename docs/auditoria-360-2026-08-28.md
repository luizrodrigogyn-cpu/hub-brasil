# Hub Brasil — auditoria 360 de arquitetura, acesso e segurança

Data da verificação: 28/08/2026

## Resumo executivo

O Hub Brasil possui autenticação de produção, separação básica entre cliente, fornecedor e gestor, controles de propriedade nas rotas principais, testes negativos A/B, observabilidade, varredura de segredos, análise de dependências, CodeQL, Bot Fight Mode, rate limiting, HTTPS obrigatório, TLS Full (strict) e HSTS.

O sistema ainda não deve ser apresentado como uma plataforma multi-tenant com RLS. Não existe `tenant_id`, o Cloudflare D1 não oferece RLS SQL nativa e parte do isolamento continua distribuída pelas rotas. Também não existe catálogo geral de módulos/feature flags, a captura de erro não possui screenshot/fila/alerta externo e o deploy automático da Cloudflare não espera o CI de segurança concluir.

## 3. Multi-tenancy e isolamento

### Estado real

O produto atual é um marketplace compartilhado. Não há tabela de organizações nem coluna `tenant_id`. O isolamento usa:

- `auth_user_id`/`user_id` para dados pessoais;
- `supplier_id` para dados empresariais;
- sessão Clerk para descobrir o ator;
- filtros de propriedade nas rotas;
- políticas centralizadas para conversas, cotações e recursos do fornecedor;
- seis testes negativos entre usuário/fornecedor A e B.

Isso reduz vazamento horizontal, mas não constitui multi-tenancy completo. As políticas centrais cobrem somente alguns fluxos; outras rotas ainda repetem autorização manualmente.

### Para atender multi-tenancy de verdade

1. Criar `organizations` e `organization_members`.
2. Adicionar `organization_id` obrigatório a toda linha privada empresarial.
3. Derivar a organização da sessão e da membership, nunca do corpo da requisição.
4. Fazer todo `SELECT`, `UPDATE` e `DELETE` privado combinar ID do recurso e organização.
5. Criar índices compostos iniciando por `organization_id`.
6. Testar leitura, alteração e exclusão cruzadas em todas as APIs.
7. Para isolamento físico máximo, usar um D1 por organização.

## 4. RLS — trava dentro do banco

Cloudflare D1 usa SQLite e não oferece políticas de Row Level Security equivalentes às do PostgreSQL. Portanto, não é possível declarar uma política RLS nativa no banco atual.

As alternativas são:

- manter uma camada obrigatória de autorização no Worker, com acesso negado por padrão;
- criar views/consultas escopadas, repositórios de dados obrigatórios e testes de integração;
- usar um D1 separado por organização para isolamento físico;
- migrar dados privados para PostgreSQL caso RLS SQL nativa seja requisito contratual.

Situação: proteção equivalente na aplicação está parcialmente implementada; RLS nativa não está implementada e não é suportada pelo D1.

## 5. Secrets management

### Confirmado

- Nenhuma chave secreta conhecida foi encontrada nos 122 arquivos versionados.
- `.env`, `.dev.vars` e `.wrangler-auth` não são versionados.
- `CLERK_SECRET_KEY` está armazenada como segredo no Cloudflare.
- O token de backup pertence ao GitHub Actions Secrets.
- O deploy usa `--keep-vars`, evitando apagar variáveis do Worker.
- A chave pública do Clerk é pública por definição e não precisa ser tratada como senha.

### Lacuna

O scanner próprio reconhece apenas padrões específicos de Clerk, GitHub, AWS, chave privada e token Cloudflare. Ele pode não detectar tokens novos ou segredos de outros fornecedores. Recomenda-se complementar com GitHub Secret Scanning e uma ferramenta como Gitleaks.

Política: chave API, senha, token, signing secret e chave privada nunca entram no código, configuração versionada, log, screenshot ou mensagem de erro.

## 6. Catálogo de funcionalidades e feature flags

Não existe um catálogo geral de módulos nem feature flags globais ou por cliente. O sistema possui módulos funcionais, mas grande parte da interface continua concentrada em `app/page.tsx` e muitas ações compartilham `/api/roadmap`.

Criar futuramente:

- `features` (`key`, nome, descrição, dependências, status global);
- `organization_features` (`organization_id`, `feature_key`, status, configuração);
- serviço central `isFeatureEnabled()`;
- auditoria de toda ativação/desativação;
- módulos independentes: diretório, cotação, mensagens, avaliações, comunidade, eventos, créditos, destaques, alertas e relatórios.

Feature flag controla disponibilidade; nunca substitui autorização.

## 7. Reportar erro e observabilidade

### Implementado

- Botão “Reportar problema” fixo e visível em todas as telas.
- `error.tsx` e `global-error.tsx` para falhas de renderização.
- Protocolo UUID, rota, navegador, mensagem e stack limitada.
- Endpoint com validação de origem, tipo e tamanho.
- Logs estruturados no Workers Logs, com `x-request-id`.
- Resposta amigável para erros não tratados.

### Não implementado

- screenshot automático com prévia e consentimento;
- fila assíncrona dedicada;
- painel de tickets/erros;
- alerta externo por severidade;
- vinculação explícita à versão/commit do deploy;
- rate limiting dedicado para o endpoint de relato.

Captura de tela não deve ser silenciosa. Deve pedir consentimento e permitir revisão, pois a tela pode conter telefone, mensagens, CNPJ ou outras informações pessoais.

## 9. Security audit e gate de deploy

O GitHub Actions executa lint, typecheck, testes, secret scan, auditoria de dependências, testes A/B e CodeQL.

O gate ainda não é efetivo para produção: a integração Git da Cloudflare publica cada push em `main` diretamente e não espera os jobs do GitHub Actions terminarem. Um commit com falha de segurança pode começar a ser publicado antes do CI falhar.

Correção prioritária:

1. remover o deploy automático independente da Cloudflare; ou
2. configurar proteção de `main` com PR obrigatório e checks exigidos; e
3. fazer o deploy de produção somente em job dependente de `quality` e `security` (`needs`), usando ambiente protegido e aprovação quando houver migração.

## 10. WAF, Bot Fight Mode e rate limiting

### Confirmado no painel

- Bot Fight Mode: ativo.
- JavaScript Detections: ativo.
- DDoS da Cloudflare: proteção automática.
- Uma regra de rate limiting ativa para `POST hub.niviontech.com.br/api/roadmap`.
- Regra atual: 10 requisições por IP em 10 segundos; bloqueio por 10 segundos.

### Avaliação

A regra existe, mas está mais permissiva que o desenho acordado de 10 requisições por minuto com bloqueio prolongado. Além disso, protege somente `/api/roadmap`.

Prioridade: ajustar a janela/duração conforme o uso real e criar proteção específica para mensagens, avaliações, uploads e `/api/error-reports`. Login/cadastro são atendidos pelo Clerk, mas devem ser monitorados e protegidos conforme os endpoints efetivamente usados.

## 11. HTTPS, TLS e HSTS

### Confirmado em produção

- SSL/TLS: **Full (strict)**.
- Always Use HTTPS: ativo.
- HTTP redireciona para HTTPS.
- HTTPS responde com `Strict-Transport-Security: max-age=31536000`.
- `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` e `X-Request-ID` ativos.

### Pendências de endurecimento

- HSTS está aplicado pelo Worker ao Hub, não pela configuração geral da zona.
- Não usa `includeSubDomains` nem `preload`, o que é correto até todos os subdomínios serem auditados.
- Minimum TLS Version da zona permanece no padrão TLS 1.0; avaliar elevar para TLS 1.2 após confirmar compatibilidade.
- CSP ainda não existe; testar primeiro em `Content-Security-Policy-Report-Only` por causa do Clerk e dos recursos externos.

## 12. Prioridade recomendada

### P0 — antes de afirmar que existe isolamento empresarial completo

1. Tornar o CI um bloqueio real antes do deploy da Cloudflare.
2. Decidir formalmente se o Hub é marketplace compartilhado ou SaaS multi-tenant.
3. Se multi-tenant, implementar organizações e `organization_id` em todas as linhas privadas.
4. Expandir testes A/B para as APIs e o D1 real de teste.

### P1 — segurança operacional

1. Ampliar rate limiting para os endpoints abusáveis e rever a janela da cotação.
2. Implementar fila e alertas para erros; screenshot somente com consentimento.
3. Complementar o scanner de segredos.
4. Adicionar testes de integração, E2E e smoke test pós-deploy.
5. Avaliar TLS mínimo 1.2 e CSP report-only.

### P2 — evolução do produto

1. Criar catálogo de módulos e feature flags.
2. Separar `app/page.tsx` e `/api/roadmap` por domínio funcional.
3. Considerar D1 por organização ou PostgreSQL com RLS, conforme o modelo comercial e contratual.
